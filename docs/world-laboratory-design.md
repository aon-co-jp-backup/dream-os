# World Laboratory構想 — 設計文書(2026-08-06、設計のみ・未実装)

> **位置づけ**: これは`dream-os`のサブ構想として、家庭の安価なPC・タブレット・
> スマホをインターネット越しに束ね、個人では持てない研究所/大学/メーカー
> 規模のAI開発環境をボランティアベースで提供する、という方向性の**設計
> 文書**。ユーザー指示「Ｃ(World Laboratory構想の本格設計)とＤ(一旦
> 区切ってopen-directx優先に戻る)を集中して」を受け、実装ではなく設計を
> 今回のゴールとする。実装着手は次回以降、open-directxの完成度向上が
> 一段落してから検討する。

## 1. 目的・非目的

**目的**: 世界中の個人が持つPC/タブレット/スマホの余剰計算資源(GPU/NPU/
CPU)を、AI(LLM推論・学習・データ処理等)のワークロードへボランティア
提供できる分散基盤を設計する。

**非目的(今回のスコープ外として明記)**:
- 暗号資産の採掘そのものが目的ではない(前節の`sha256d_mine`はあくまで
  「GPU計算ディスパッチが正しく動くか」を検証するための題材であり、
  World Laboratory自体はマイニング専用の構想ではない)。
- 実装(コード)は今回書かない。設計・実在先例の調査・アーキテクチャ
  方針の確定のみ。

## 2. 実在の先行事例からの教訓(2026-08-06調査、`CLAUDE.md`参照)

| 先例 | 教訓として採用する設計要素 |
|---|---|
| [BOINC](https://boinc.berkeley.edu/) | 中央コーディネータがワークユニットを分割配布→クライアントが計算→結果を返す、という基本構造。**同一ワークユニットを複数の独立したクライアントへ配り、結果を突き合わせて多数決検証する**(信頼できないボランティアノードからの不正/誤り結果への対策)。 |
| [Folding@home](https://foldingathome.org/) | GPU/CPU双方への対応、大規模な参加者数でも成立する疎結合設計。 |
| [Golem Network](https://www.golem.network/) | 計算資源の提供者(provider)と要求者(requestor)を分離し、資源のマーケットプレイス的な構造にする発想。 |
| Petals(分散LLM推論) | 巨大なモデルを層(layer)単位で複数ノードへ分割し、パイプライン的に推論を分散する——単一ノードでは収まらないモデルサイズへの対応パターン。 |

## 3. アーキテクチャ方針(暫定案)

### 3.1 全体構成(4層、2026-08-06にユーザー指示で3層から拡張)

ユーザー指示「open-web-server・RPoem・open-raid-z・aruaru-dbのACID互換・
ZFS互換の4層4重通信の技術もdream-osに実装、移植して」を受け、当初の
3層(コーディネータ/ワーカー/実行基盤)に、**通信・永続化層**を明示的な
第4層として追加した。日英再調査(下記2.1節)の結果、BOINC自体の結果
検証は「N台への複製配布+多数決」が中心で暗号学的な改ざん検知・リプレイ
対策は標準機構として持たないことを確認——このエコシステムの
`open-web-server-wire`(4層防御通信: TLS→相互認証→AEAD暗号化→
リプレイ対策)は、BOINCが本来必要とする「不正な結果の改ざん検知」
「同一結果のリプレイによる多数決の不正操作(Sybil的攻撃の一種)を防ぐ」
という要件に対し、**BOINC自体よりも一段強固な保証を提供できる**ため、
World Laboratoryの差別化要素として積極的に採用する。

```
[コーディネータ層]  ← このエコシステムの既存資産を再利用
  RPoem/open-web-server(HTTP API、既存のテナント管理・認証基盤)
  + タスクキュー(ワークユニットの分割・配布・結果集約)
       │
       ▼
[通信・永続化層]  ← 新規crate dream-os-wire(実装済み、下記3.4節参照)
  open-web-server-wire(SecureChannel: AEAD暗号化+リプレイ対策)で
  ワーカー→コーディネータの結果送信を保護。将来的にopen-web-server-ledger
  (PostgreSQL/aruaru-db/マルチリージョン同期/独立監査ログの4重永続化)を
  結果の永続化先として再利用する設計(open-raid-z=ZFS互換ストレージ、
  aruaru-db=ACID互換DUAL DATABASEの一部)。
       │  SecureChannelで暗号化・改ざん検知・リプレイ拒否されたフレーム
       ▼
[ワーカー層]  ← dream-os-kernelを拡張
  各ボランティアPC/タブレット/スマホ上で常駐する軽量エージェント。
  MiningPowerProfile(既存実装)を流用し、ボランティアが「PCの何%を
  提供するか」を電力出力調整と同じ発想で設定できる。
       │
       ▼
[実行基盤層]  ← 既存の open-cuda / opencuda-vulkan
  GPU(Vulkan Compute)・将来的にはNPU(別バックエンド)への実ディスパッチ。
```

**設計判断**: 新規に何かを一から作るのではなく、既存の4つの資産
(RPoem/open-web-server=コーディネータ候補、open-web-server-wire/
open-web-server-ledger=通信・永続化層、dream-os-kernel=ワーカー
エージェントの土台、opencuda-vulkan=実行基盤)を繋ぎ合わせる設計とする
——「ゼロから分散システムを書く」のではなく「このエコシステムが既に
持つ部品を、分散ワークロード配布という新しい文脈で組み立て直す」という、
これまでのDreamOS設計方針(ChromeOS/crosvm型のアプローチ)と一貫させる。

### 2.1 再調査結果(2026-08-06、日英でGoogle/GitHub再調査)

- **BOINCの結果検証は暗号学的な改ざん検知・リプレイ対策が標準機構
  ではない**: 調査によれば、BOINCは「信頼できないボランティアPCからの
  結果を信用しない」という前提のもと、**複製配布ベースの検証
  (replication-based validation、同一ジョブを2台以上の無関係なPCで
  実行し、出力が一致すれば正当とみなす。不一致なら3台目を追加し、
  一致するクォーラムに達するか上限に達するまで繰り返す)**を主軸に
  据えている([BOINC Wiki: SecurityIssues](https://github.com/BOINC/boinc/wiki/SecurityIssues))。
  また、悪意ある実行ファイル配布への対策として**コード署名**
  (プロジェクトサーバーへの侵入があっても、クライアントは署名されて
  いない偽の実行ファイルを受理しない)を用いる。
- **AEAD+シーケンス番号によるリプレイ対策は業界標準パターンと一致**:
  「典型的な通信セキュリティプロトコルはAuthenticated Sequence Number
  (ASN)技術でアンチリプレイを提供する——送信メッセージごとに
  シーケンス番号を認証済み部分に含め、受信側が既知の全シーケンス番号と
  異なることを確認する」という一般的な設計原則を確認した。これは
  `open-web-server-wire::SecureChannel`が既に実装している設計
  (seq/timestampをAEADのAAD〈Associated Data〉として暗号文に紐付け、
  受信側が再送・鮮度外タイムスタンプを拒否する)と完全に一致する。
- **結論**: World Laboratoryは、BOINC型の「複製配布+多数決」(§3.3)と、
  このエコシステムが既に持つ「AEAD+リプレイ対策による結果フレーム自体の
  改ざん検知」(§3.4)を**両方組み合わせる**ことで、BOINC単体・
  素のAEAD単体のどちらよりも強固な結果検証を実現できる見込み。

### 3.2 ワークユニット(タスク)の設計

- **粒度**: 1ワークユニット = 1回のカーネルディスパッチ相当
  (例: `sha256d_mine`なら「nonce範囲X〜Yのバッチ」、将来のLLM推論なら
  「入力バッチNのforward pass」)。既存の`MiningWorker::mine_batch`の
  「1バッチ」という単位がそのままワークユニットの最小粒度として使える。
- **べき等性**: 同一ワークユニットを複数ノードへ再配布しても安全に
  再実行できる設計(既存の`nonce_base`+`count`のような、状態を持たない
  純粋な入力パラメータで表現する)。

### 3.3 結果検証・信頼性(BOINCパターンの踏襲)

- **N-of-M多数決検証**: 1ワークユニットをM台の独立したノードへ配布し、
  N台以上が同じ結果を返せば正当な結果として採用する(既存の
  `open-web-server-ledger::MultiRegionReplicator`が既に持つ
  「N-of-M縮退モード」の設計パターンを、DB書き込みではなく計算結果検証
  へ転用できる可能性がある——車輪の再発明を避ける観点で次回検討)。
- **評判スコア**: 過去の結果が多数決と一致した実績に基づき、ノードごとの
  信頼度を追跡する(BOINCの"credit"システムに相当)。

### 3.4 通信・永続化層の実装(2026-08-06、設計だけでなく実際に実装・検証済み)

新規crate`crates/dream-os-wire`(`open-web-server-wire`へのpath依存)を
実装した。**設計文書に留めず、実際にコードを書いて実機で動作検証した**:

- `WorkResultEnvelope`(ワークユニットID・ワーカーID・結果本体のJSON)を
  `WorkerChannel::submit()`で`SecureChannel::encrypt()`経由の暗号化
  フレームへ変換、`CoordinatorChannel::receive()`で復号・検証する薄い
  ラッパー。
- **実際に検証した3つのシナリオ**(`tests/secure_channel_integration.rs`、
  `cargo test -p dream-os-wire --release`3件全green):
  1. 正常な結果送信→受信(往復一致)。
  2. **同一結果フレームの単純リプレイを拒否**(悪意あるノードが多数決を
     水増しするために同じ結果を複数回送りつける攻撃を模擬)。
  3. **改ざんされた結果フレームを拒否**(AEADタグ検証で復号自体が失敗、
     でっち上げた偽の計算結果が「一見正しく見える形」でコーディネータへ
     届くことを防ぐ)。

**実装しなかったもの(正直な開示)**: (a) 4重伝送路(TCP/UDP/QUIC/MPTCP)
は`open-web-server-wire`に既存だが今回は配線せず、ペイロード層
(SecureChannel)のみ。(b) 4重DB永続化(PostgreSQL/aruaru-db/マルチ
リージョン同期/独立監査ログ、`open-web-server-ledger`)は実DBインスタンス
がこのマシンに無いため配線せず、設計方針の記録のみ。(c) TLS終端・相互
認証(第1層・第2層)は、将来コーディネータをRPoem/open-web-server上に
実装する際にそちら側が担う想定で、今回のPoCでは検証していない。詳細は
`crates/dream-os-wire/src/lib.rs`のモジュールdocに実装スコープを明記。

### 3.4 セキュリティ・Sybil耐性(今回は方針のみ、実装未着手)

- 悪意あるノードが偽の結果を大量に送りつける攻撃(Sybil攻撃)への対策は、
  上記N-of-M多数決だけでは不十分(結託した複数の偽アカウントが同じ誤り
  結果を返せば多数決を突破できる)。実運用では、参加ノードの認証(既存の
  `KeyGuardian`/OAuth連携基盤が使えないか検討)・ランダムなワークユニット
  割り当て(結託を困難にする)等、追加の設計が必要——今回は「必要な
  検討事項」として記録するに留め、具体的な対策設計は次回以降とする。

## 5. 正直な結論(2026-08-06更新)

World Laboratory構想は技術的に実現不可能ではなく、実在する先行事例
(BOINC等)から実務上の設計パターンを転用できる見込みがある。**通信・
永続化層(第4層)については、設計に留まらず`crates/dream-os-wire`として
実際にコードを実装し、正常系・リプレイ攻撃・改ざん攻撃の3シナリオを
実機で検証済み**——これはこのエコシステムの既存資産(open-web-server-
wire)の再利用による具体的な前進である。

一方、本格的な実運用には、(a) コーディネータ側のワークユニット配布・
複製配布(N-of-M)ロジックの実装、(b) 4重DB永続化(open-web-server-
ledger)の実配線、(c) 外部ボランティアの認証・評判スコア・Sybil耐性、
という単一マシンでのGPU/NPU活用とは別レイヤーの相当な開発規模が
引き続き必要であり、**今回は通信・永続化層(第4層)の実装・検証までを
成果とし、コーディネータ本体の実装はopen-directxの完成度向上が優先で
ある現在の方針を踏まえ、次回以降の判断に委ねる**。
